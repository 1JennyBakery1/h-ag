    智能旅行助手

    24 分钟等级: 进阶

    智能旅行助手是一个全栈 Agent 应用，它能将自然语言的旅行需求转化为结构化、符合预算的多日行程。它展示了 Agent 工程的两个互补层面：基于 HelloAgents 框架构建并可通过 MCP 调用真实工具的多 Agent 编排层，以及将基础 LLM 转化为生产级规划器（Planner）的后训练流水线，该规划器能够严格遵守硬性预算约束、基于工具返回的候选结果选择餐厅，并输出稳定的 JSON。这两层共同阐明了本项目的核心论点：能被结构化的应交由工程处理；能被规则校验的应转化为评估；只有真正需要模型判断的才应进入 SFT 或偏好训练。

    来源: README.md, Extra12-旅行助手后训练实战.md

    系统架构

    该助手在多 Agent 系统中遵循四阶段流水线。三个专家 Agent —— 景点搜索、天气查询和酒店推荐 —— 各自调用高德地图 MCP 工具来收集真实数据。第四个规划 Agent 将它们的输出综合为结构化的 TripPlan JSON。前端提交结构化的 TripRequest，后端则编译供 Agent 使用的 PlannerContext。

    核心设计原则是关注点分离：每个专家 Agent 拥有狭窄的领域和单一的工具接口，而规划 Agent 负责组合逻辑但不自行调用工具。这使得各个 Agent 易于测试、替换或切换模型。

    来源: trip_planner_agent.py, trip.py

    多 Agent 编排

    MultiAgentTripPlanner 类是编排器。它实例化四个 SimpleAgent 实例，在三个工具调用 Agent 之间共享单个与高德地图 MCP 服务器连接的 MCPTool，并在 plan_trip() 内部执行严格的四步序列：

    步骤Agent调用工具输出
    1景点 Agentamap_maps_text_search请求城市 + 偏好关键词的原始 POI 文本
    2天气 Agentamap_maps_weather多日天气预报文本
    3酒店 Agentamap_maps_text_search (keywords="酒店")该城市的酒店 POI 文本
    4规划 Agent(无工具)完整的 TripPlan JSON

    每个专家 Agent 的系统提示词都强制要求基于工具返回结果生成内容：提示词明确指示 Agent 不得捏造数据，并指定了精确的 [TOOL_CALL:...] 格式。这是应用层对后训练原则“不让模型猜测业务事实”的呼应。

    MCPTool 仅创建一次，并通过 add_tool() 在各 Agent 间共享。MCP 服务器进程（amap-mcp-server）通过 uvx 启动，并基于 stdio 进行通信。如果服务器启动缓慢，首次 Agent 调用将阻塞直到服务器就绪——在生产环境中建议考虑预热。

    来源: trip_planner_agent.py, amap_service.py

    数据模型与 API 契约

    系统的数据完整性依赖于 Pydantic 模型，这些模型强制执行产品协议——即后训练流水线随后冻结并据此进行评估的同一协议。

    请求模式

    字段类型描述
    citystr目的地城市
    start_datestr开始日期 (YYYY-MM-DD)
    end_datestr结束日期 (YYYY-MM-DD)
    travel_daysint旅行天数 (1-30)
    transportationstr交通偏好
    accommodationstr住宿偏好
    preferencesList[str]旅行风格标签
    free_text_inputOptional[str]额外需求

    响应模式

    字段类型描述
    daysList[DayPlan]每日行程，包含景点、餐饮、酒店
    weather_infoList[WeatherInfo]每日天气预报
    budgetBudget分项总计：景点、酒店、餐饮、交通
    overall_suggestionsstr通用旅行建议

    Budget 模型是后训练评估重点关注的部分。它分解为四个细项加上一个 total，后训练流水线会检查算术一致性（part_sum == total）、硬性预算约束（total ≤ requested_budget）以及重算预算的正确性（根据细项数据独立重算）。

    来源: schemas.py

    前端集成

    前端是基于 Vite 和 Ant Design Vue 构建的 Vue 3 + TypeScript 单页应用（SPA）。它通过一个三段式表单收集结构化的旅行偏好：

    1. 目的地与日期 —— 城市输入、日期选择器、自动计算行程天数
    2. 偏好设置 —— 交通方式、住宿档次，以及基于复选框的兴趣标签（历史文物, 自然风光, 美食, 购物, 艺术, 休闲）
    3. 自由文本需求 —— 可选的文本域，用于饮食限制或无障碍需求等约束条件

    表单将 JSON 负载提交至 POST /api/trip/plan，并在 Result.vue 中展示生成的行程，地图标记由高德地图 JavaScript API 驱动。

    前端表单强制使用结构化输入（transportation、accommodation、preferences），而不是依赖单一的自由文本字段。这反映了后训练原则：显式提交结构化字段，使模型无需猜测业务事实。 如果你扩展此项目，可在表单中增加 party（旅行者人口统计信息）和 budget_constraint（金额 + 范围）字段，以进一步缩小规划 Agent 的任务范围。

    来源: Home.vue, index.ts

    后训练流水线：从产品协议到生产级规划器

    应用层的多 Agent 系统能生成行程，但基础 LLM 会犯可预见的错误：酒店晚数计算偏移、餐厅重复、预算算术错误，以及模型捏造未基于工具结果的 POI 数据。后训练流水线通过五个阶段的递进系统地修复了这些问题。

    流水线概述

    流水线的座右铭：提示词修正协议，SFT 学习结构，DPO 学习偏好，重排筛选最佳候选。 每个阶段都为下一阶段缩小了问题空间，且每个阶段都基于相同的冻结评测集进行验证。

    来源: Extra12-旅行助手后训练实战.md

    阶段 1：产品协议改造

    第一个也是影响最大的变更根本不是模型层面的改变。产品协议被重新设计，使得前端显式提交结构化字段（旅行团队构成、预算范围、住宿晚数），并且后端编译一个 PlannerContext，明确告知模型如何解释每个字段。

    改造前（朴素做法）改造后（结构化）
    单一自由文本："杭州4天预算3500"显式的 budget_constraint，包含金额、范围和硬性度
    模型猜测预算是人均还是总计budget_scope 字段："整趟" vs "人均"
    模型从日期范围推断住宿晚数后端计算 lodging_nights、room_count 并作为提示传入
    模型捏造餐厅名称PlannerContext 仅包含工具返回的餐厅候选

    这一改造将模型的任务从“发明旅行计划”缩小为“在结构化候选中进行选择并输出有效 JSON”——这对提示词工程和训练来说都是更容易处理的问题。

    来源: Extra12-旅行助手后训练实战.md

    阶段 2：冻结评测集

    当评估基准不断变化时（天气更新、地图候选变动、预算逻辑演进），训练结果将变得无法解释。解决方案是冻结两个评测集且永不修改其请求签名：

    评测集目的内容
    standard eval常规条件下的稳定性普通城市、预算、偏好
    hard eval压力测试边界情况多人出行、老人/儿童、严格预算、负向偏好、饮食限制

    当上下文编译逻辑更改时，仅重建工具候选和上下文——请求签名保持一致，从而保留跨运行的可比性。此外，DPO 闭合数据经验证与冻结评测集零重叠（selected_eval_signature_overlap = 0）。

    来源: Extra12-旅行助手后训练实战.md

    阶段 3：提示词调试寻找边界

    提示词调试不是为了打造一个“神级提示词”。它的核心在于分类哪些问题可以通过提示词解决，哪些需要依赖数据、规则或工程：

    问题类别提示词可修复？真正的解决方案
    输出形态（日期格式、字段缺失、JSON 破损）✅ 是提示词 + 解析器 + 校验
    餐厅基于事实（无捏造名称）⚠️ 部分提示词约束 + 基于规则的检查器
    捏造路线时长（"步行10分钟"）❌ 否输出规则过滤
    预算算术错误❌ 否工程重算 + SFT 数据

    提示词调试最有价值的产出是失败画像——一种坏案例的分类法，它决定了下游工作应将重点放在何处。

    来源: Extra12-旅行助手后训练实战.md

    阶段 4：LoRA SFT 多阶段训练

    SFT 数据由强教师模型生成，但“看起来合理 ≠ 可训练”。流水线在数据进入训练前应用了严格的审查漏斗：

    SFT 数据审查漏斗

    过滤器为何重要
    JSON / 模式有效性后端必须能够解析
    日期与天数一致性无遗漏或多余天数
    酒店与餐厅基于候选结果无捏造的 POI
    无餐饮重复（同一家餐厅反复出现）用户体验质量
    未超出硬性预算约束核心产品需求
    预算关系正确性酒店晚数 × 房间数，门票 × 出行人数

    来自旧预算协议的旧数据应归档，而非修补。混合“新协议 + 旧口径”的数据是 Agent 后训练中最常见的隐性失败——模型会学习到矛盾的模式，导致评估变得不可靠。

    多阶段 LoRA 训练计划

    所有阶段均使用带有 LoRA r32、长上下文和 bf16 的 Qwen2.5-7B-Instruct。随着训练目标的缩小，学习率单调递减：

    阶段数据学习率轮次目标
    主清洗 SFTmain_clean6e-5 / 8e-54学习稳定的 TripPlan 协议
    真实预算混合 (usage700)main_clean + realbudget 7002e-51补充预算使用模式
    预算利用率补丁 (patch700)budget patch 7001e-52测试特定预算数据能推进到何种程度
    Best-of-N 重放 600旧重放 + BoN 胜出者1e-50.5-save注入由规则筛选的更优候选
    Best-of-N 重放 1200旧重放 + 更多 BoN 胜出者1e-50.5-save提高胜出者比例

    每个阶段都从上一个适配器（adapter_name_or_path）热启动，但优化器状态会重置——这是有意为之，允许每个阶段使用适合其数据规模和难度的全新学习率计划。

    全参数 SFT：为何未成为主线

    曾进行过全参数 SFT 实验以作对比。它提升了 PlannerSoft（+3.3pp）和餐饮多样性（+6.2pp），但降低了预算算术（-4.3pp）和用户预算约束（-2.8pp）。结论：全参数训练更激进地改变了模型的“规划习惯”，但本项目的核心挑战是硬性规则下的约束满足，而非创意生成。LoRA 较低的容量在此任务中起到了隐式正则化的作用。

    指标全参数LoRA差值
    Hard Pass94.4%95.8%-1.4pp
    PlannerSoft48.0%44.7%+3.3pp
    餐饮多样性82.6%76.4%+6.2pp
    预算算术68.0%72.3%-4.3pp
    用户预算约束88.8%91.6%-2.8pp

    来源: Extra12-旅行助手后训练实战.md

    阶段 5：DPO 偏好学习与最终重排

    Best-of-N 重放 vs. 最终重排

    这两种机制结构相似，但目的不同：

    方面Best-of-N 重放最终重排
    时机训练数据构建推理时答案选择
    流程多次采样 → 规则选出胜者 → 导出为 SFT 数据多次采样 → 规则选出最佳 → 返回给用户
    目标提升下一轮训练的数据质量提升部署时的答案质量

    DPO 对构建

    DPO 对被约束为双双通过 hardpass——chosen 和 rejected 均为有效计划，仅在偏好质量上有所不同。这确保了 DPO 学习的是有效选项间的偏好，而非格式纠正：

    相同的 PlannerContext
  → chosen:  schema ✓, hardpass ✓, planner_soft ✓
  → rejected: schema ✓, hardpass ✓, 但 budget/repeat/preference 失败

    主要指标从 hardpass 转向了 PlannerSoft——一个结合了预算契合度、餐饮多样性、景点多样性和预算关系正确性的综合指标。

    DPO 阶段递进

    阶段目标关键结果
    高置信度 DPO 试验验证长上下文 DPO 可行流水线验证通过
    PlannerSoft 规则 DPO将优化从 hardpass 转向 planner_soft首个可用的 DPO 检查点 (ckpt25)
    PlannerSoft 扩展 + 直接锚点使用直接偏好扩展 planner_soft 数据稳定的扩展基线 (ckpt126)
    PlannerSoft 清洗单次生成更大规模的清洗数据最佳单次生成版本 (ckpt138)
    预算闭合 DPO针对预算保守性、超支、重复单次生成遭遇瓶颈，但候选池改善有利于重排

    最终重排的多候选结果

    版本Hard PassPlannerSoft重算预算 Soft
    扩展基线 (ckpt126)98.4%66.9%48.5%
    PlannerSoft 清洗单次生成 (260519 ckpt138)98.4%71.5%50.9%
    预算闭合第 2 轮 + 4 候选重排 (260521 ckpt64)99.4%80.6%68.2%

    关键洞察：最佳单次生成检查点与最佳重排检查点并非同一个模型。单次生成衡量的是平均采样质量；重排衡量的是候选池中是否包含可选的良好答案。预算闭合 DPO 轮次并未提升单次生成分数，但丰富了候选池，使重排变得更为有效。

    来源: Extra12-旅行助手后训练实战.md

    坏案例集：三个最有价值的错误

    后训练中最具启发性的产物不是成功案例，而是迫使架构做出改变的反复出现的失败模式。

    1. 预算算术崩溃

    一笔硬性预算为 ¥3,200 的济南 3 日游，总计产出了 ¥5,088——子项总和（¥4,988）和声明的总计（¥5,088）均错误，且双双超出硬性约束。这导致将预算评估拆分为两条路径：一条检查模型声明的 budget.total，另一条独立从细项重算。

    budget_arithmetic_inconsistent: part_sum=4988, total=5088, diff=-100
meal_budget_inconsistent: expected=1928, reported=1748
budget_hard_constraint_exceeded: requested=3200, total=5088

    2. 餐饮重复惰性循环

    一笔长沙 4 日家庭游在 12 顿饭中有 4 顿使用了同一家餐厅（新长福 世嘉店），包括同一天的午餐和晚餐。修复方法是三层约束：同一天的午餐/晚餐不能重复，同一家餐厅家族有次数上限，餐厅必须基于工具返回的候选结果。

    meal_same_day_lunch_dinner_repeat: 2026-03-08 lunch/dinner both 新长福(世嘉店)
meal_repeat_too_many: name_key=新长福, count=4, max_allowed=3

    3. 酒店晚数 × 房间数低估

    一笔北京 3 日朋友游（3 人）需要 2 间房 × 2 晚 = 最低 ¥6,000，但模型报告为 ¥3,000（1 间房 × 2 晚）。这无法仅通过提示词修复——后端必须从 party.total 显式计算 room_count 并将其作为提示传入。

    hotel_budget_underestimated:
  lodging_nights=2, party_total=3, room_count=2
  expected_min=6000, reported=3000

    来源: Extra12-旅行助手后训练实战.md

    核心要点

    从该项目中提炼出的十项原则，构成了适用于任何 Agent 后训练工作的决策框架：

    1. 首先改造产品协议。 如果一个字段可以被结构化，就不要让模型去猜。
    2. 仔细编译上下文。 模型应在候选中进行选择，而不是发明事实。
    3. 冻结评测集。 训练数据可以变，但基准测试不能变。
    4. 使用提示词调试寻找边界。 提示词可修复的问题交由提示词；其余的交由数据、规则或工程。
    5. 审查教师模型输出。 “看起来合理” ≠ “可训练”。过滤模式、基于事实和约束的正确性。
    6. 分阶段推进 LoRA SFT。 每一轮应针对一个主要问题类别。
    7. 区分 Best-of-N 重放与最终重排。 一个用于构建训练数据；另一个用于选择部署答案。
    8. DPO 仅在有效候选之间进行。 修复格式的配对教导的是格式，而非偏好。
    9. 防止评测泄漏至训练数据。 签名重叠检查成本低廉且至关重要。
    10. 分解指标。 Hardpass、PlannerSoft、预算算术和重算预算是独立的信号——不要将它们压缩为一个分数。

    能被结构化的，交由工程处理；能被规则校验的，转化为评估；只有真正需要模型判断的，才进入 SFT 或偏好训练。

    来源: Extra12-旅行助手后训练实战.md
