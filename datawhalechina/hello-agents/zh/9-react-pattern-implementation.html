    ReAct 模式实现

    19 分钟等级: 进阶

    ReAct 模式——即 Reasoning（推理）与 Acting（行动）的简称——是一种基础范式，它将大型语言模型从被动的文本生成器转变为能够与外部世界交互的自主 Agent。纯链式思考提示词在孤立状态下进行推理，而纯行动驱动的方法则在没有反思的情况下采取行动，与之不同的是，ReAct 将思考、行动和观察紧密交织在一个协同循环中。本页将通过生产级实现，从第一性原理深入剖析 ReAct 范式，并以 datawhalechina/hello-agents 代码库作为主要参考。

    ReAct 为何出现：推理与行动的鸿沟

    在 Shunyu Yao 于 2022 年提出 ReAct 之前，Agent 的方法主要分为两个互不相通的阵营。链式思考提示词能够引导模型进行复杂的逻辑推理，但始终受限于模型的参数化知识——无法获取实时数据、执行精确计算或与 API 交互。相反，行动驱动系统能够调用工具，却缺乏决定使用哪个工具、何时使用以及如何解读结果的推理支架。ReAct 的洞见在架构上极为优雅：思考与行动相辅相成。思考引导行动；行动结果纠正思考。这种双向反馈循环使得 ReAct 成为实践中最广泛采用的 Agent 范式。

    方面链式思考纯行动ReAct
    外部工具使用❌ 否✅ 是✅ 是
    显式推理轨迹✅ 是❌ 否✅ 是
    动态错误纠正❌ 否（静态）❌ 否（被动反应）✅ 是（逐步）
    可解释性部分低高（完整轨迹）
    幻觉风险高（无事实依据）中低（由观察提供事实依据）

    来源：Chapter4-Building-Classic-Agent-Paradigms.md

    思考-行动-观察循环：核心机制

    ReAct 范式将 Agent 的每一步围绕三个固定阶段进行构建。在每个时间步 t，Agent 的策略（即 LLM，记作 π）基于原始问题 q 及所有先前的行动-观察对，生成思考 th_t 和行动 a_t：

    (tht,at)=π(q,(a1,o1),…,(at−1,ot−1))\left(th_t, a_t\right) = \pi\left(q, (a_1, o_1), \ldots, (a_{t-1}, o_{t-1})\right)(tht​,at​)=π(q,(a1​,o1​),…,(at−1​,ot−1​))

    随后，环境的工具 T 执行行动 a_t 并返回观察 o_t：

    ot=T(at)o_t = T(a_t)ot​=T(at​)

    此循环将一直持续，直到模型认定任务已完成。

    关键的架构洞察在于：历史记录是 Agent 唯一的记忆。每次循环迭代都会将行动-观察对追加到不断增长的上下文中，然后将其重新注入到下一个提示词中。这意味着 LLM 能够“看到”目前所做的一切，并据此进行推理。

    来源：Chapter4-Building-Classic-Agent-Paradigms.md, ReAct.py

    架构深入剖析：三个相互连接的组件

    本仓库中的 ReAct 实现清晰地解耦为三个在运行时协作的独立模块。理解它们的边界对于调试和扩展至关重要。

    组件 1：HelloAgentsLLM — 推理引擎

    HelloAgentsLLM 类将所有 LLM 交互细节封装在一个 think() 方法中。它从环境变量（LLM_MODEL_ID、LLM_API_KEY、LLM_BASE_URL）加载配置，初始化一个兼容 OpenAI 的客户端，并返回完整的文本响应。该方法内部使用流式模式进行实时输出，但会将所有数据块拼接并返回完整的字符串——这一设计选择简化了下游的解析工作。

    默认设置 temperature=0 是有意为之——ReAct Agent 需要确定且可复现的输出。提高 temperature 引入的随机性可能会破坏思考-行动解析流程的稳定性。仅在你的用例明确需要创造性探索时才提高该值。

    来源：llm_client.py

    组件 2：ToolExecutor — 行动调度器

    ToolExecutor 实现了注册表模式，将工具定义与工具调用解耦。工具在运行时通过名称、描述和可调用函数进行注册。Agent 无需了解实现细节——它只看到格式化后的描述字符串，并按名称调用工具。

    描述字段是整个工具机制中最关键的部分——它是 LLM 决定何时以及如何使用工具的依据。像“一个搜索工具”这样模糊的描述会导致不可靠的工具选择；而像“一个网络搜索引擎。当你需要回答有关时事、事实和知识库中未找到的信息的问题时，请使用此工具。”这样精确的描述，则为 LLM 提供了明确的决策标准。

    内置的 search 工具展示了智能的结果解析：它优先提取 Google 的 answer_box 和 knowledge_graph 字段（直接的事实性答案），仅在无法获取结构化答案时才回退到常规结果片段。这种分层方法最大化了 Agent 观察步骤的信噪比。

    来源：tools.py

    组件 3：ReActAgent — 协调器

    ReActAgent 类是 ReAct 三个阶段汇聚为单一循环的地方。其架构可以通过四个子职责来理解：

    子职责方法目的
    提示词构建run() (第 30-36 行)将工具、问题、历史记录注入模板
    LLM 调用run() → llm_client.think()发送格式化提示词，接收原始文本
    输出解析_parse_output(), _parse_action(), _parse_action_input()通过正则表达式提取思考/行动
    循环控制run() while 循环 + max_steps迭代或终止

    来源：ReAct.py

    提示词模板：范式的栖身之所

    整个 ReAct 机制由单一的提示词模板驱动。该模板同时履行四项功能：角色定义、工具展示、格式强制和上下文注入。

    有四个结构元素值得关注：

    1. 角色设定（"你是一个有能力调用外部工具的智能助手"）——在任何细节给出之前，先锚定 LLM 的行为模式。
    2. 工具目录（{tools}）——通过 ToolExecutor.getAvailableTools() 动态注入，因此添加新工具无需修改模板。
    3. 格式约定（思考/行动结构）——严格的格式使得正则解析成为可能。没有它，Agent 无法从自由格式的 LLM 输出中可靠地提取可执行的意图。
    4. 历史注入（{history}）——累积所有先前的行动-观察对，为 LLM 的每一个新推理步骤提供完整的轨迹上下文。

    提示词的脆弱性既是它的优势，也是它的致命弱点。即使是微小的措辞改变也可能极大地改变 LLM 的行为。在调试时，务必打印完整渲染的提示词（.format() 之后）——而不仅仅是模板——以准确查看 LLM 接收到了什么。

    来源：ReAct.py, Chapter4-Building-Classic-Agent-Paradigms.md

    解析流程：从自由文本到结构化意图

    在 LLM 返回原始文本后，Agent 必须提取两个结构化字段：思考（用于日志记录和可解释性）和行动（用于执行）。解析流程按顺序使用三个基于正则表达式的方法：

    _parse_output(text) 在 Action: 边界处拆分 LLM 响应。正则表达式 r"Thought:\s*(.*?)(?=\nAction:|$)" 捕获 Thought: 与 \nAction: 或文本结尾之间的所有内容，而 r"Action:\s*(.*?)$" 捕获从 Action: 到文本结尾的所有内容。re.DOTALL 标志确保能正确捕获多行内容。

    _parse_action(action_text) 使用 r"(\w+)\[(.*)\]" 将类似 Search[Huawei latest phone] 的行动字符串分解为元组 ("Search", "Huawei latest phone")。这种括号分隔的格式简单却有效——它避免了 JSON 解析的复杂性，同时对于单参数工具调用仍保持明确性。

    _parse_action_input(action_text) 提取 Finish[answer] 指令中括号内的内容，仅返回最终答案字符串。

    方法输入模式输出失败模式
    _parse_outputThought: ... \n Action: ...(thought, action) 元组返回 (None, None)
    _parse_actionToolName[input](tool_name, tool_input) 元组返回 (None, None)
    _parse_action_inputFinish[answer]answer 字符串返回 ""

    一个关键的设计决策：当解析失败时，Agent 不会崩溃。相反，它会向历史记录中追加一条警告（"无效的Action格式，请检查"）并继续循环，给 LLM 在下一次迭代中自我纠正的机会。

    来源：ReAct.py

    执行轨迹：完整演练

    考虑问题 "华为最新的手机是哪一款？它的主要卖点是什么？"（What is Huawei's latest phone? What are its main selling points?）。Agent 分两步执行：

    步骤 1：首个思考-行动-观察循环

    LLM 推理出其缺乏当前知识，决定进行搜索：

    Thought: To answer this question, I need to search for Huawei's latest
released phone model and its main features. This information may be
outside my existing knowledge base, so I need to use a search engine.
Action: Search[Huawei latest phone model and main selling points]

    ToolExecutor 将此分派给 search 函数，该函数查询 SerpApi 并返回包含结构化搜索结果的观察——包括答案框、知识图谱条目或常规片段。

    步骤 2：综合与完成

    凭借观察数据，LLM 综合出答案：

    Thought: Based on the search results, Huawei's latest flagship models
include Mate 70 and Pura 80 Pro+. I can now provide a comprehensive answer.
Action: Finish[According to the latest information, Huawei's latest phones
may be HUAWEI Pura 80 Pro+ or HUAWEI Mate 70...]

    Finish 行动触发立即返回——Agent 不会进入下一次循环迭代。整个过程恰好消耗了 2 次 LLM 调用和 1 次工具调用。

    来源：Chapter4-Building-Classic-Agent-Paradigms.md, ReAct.py

    优势、局限与调试策略

    核心优势

    • 高可解释性：Thought 链提供了完整的审计轨迹——你可以确切地看到 Agent 为何选择每个行动，这对于建立信任和合规性极具价值。
    • 动态错误纠正：如果搜索返回了无关结果，Agent 可以在下一步重新构建查询——它不会被锁定在预先计算的方案中。
    • 工具协同：该范式自然地将“做什么”（LLM 推理）与“怎么做”（工具执行）分离开来，使得每一层能够独立演进。

    固有局限

    • LLM 依赖：整个系统取决于 LLM 遵循格式指令、正确推理和选择合适工具的能力。较弱的模型会产生格式错误的行动、不正确的工具选择或虚构的工具名称。
    • 串行执行成本：每一步都需要一次完整的 LLM API 调用。对于需要 5 步以上的任务，累积延迟和 token 成本呈线性增长。
    • 提示词脆弱性：微小的模板修改可能会引发行为改变的连锁反应。格式约定是一种软约束——没有编译器来强制执行它。
    • 局部最优风险：逐步贪婪决策模式缺乏全局规划。Agent 可能会沿着局部看似可行但全局次优的路径前进。

    从零到框架：演进之路

    code/chapter4/ 中的 ReActAgent 是一个从零开始的实现，旨在实现最大的透明度——思考-行动-观察循环的每一行都是可见且可修改的。当你走向生产应用时，相同的模式会再次出现在 code/chapter7/my_react_agent.py 基于框架的实现中，其中 ReActAgent 继承自框架基类，并将工具管理委托给 ToolRegistry：

    方面第 4 章（从零开始）第 7 章（框架）
    LLM 客户端HelloAgentsLLM（独立）HelloAgentsLLM（框架）
    工具注册表ToolExecutor（基于字典）ToolRegistry（框架）
    Agent 基类object来自 hello_agents 的 ReActAgent
    历史格式List[str]List[Message]
    提示词模板内联常量可通过构造函数自定义

    框架版本保留了相同的核心循环（构建提示词 → 调用 LLM → 解析 → 执行 → 追加历史），但增加了生产级的便利性，如带类型的 Message 对象、可配置的提示词模板，以及达到 max_steps 时的优雅降级处理。

    接下来是什么

    ReAct 的逐步反应机制非常强大，但它并不是构建 Agent 认知的唯一方式。当任务需要保证步骤顺序的长周期规划时，计划与求解及反思 范式提供了一种根本不同的架构：先计划，后执行。当你准备好了解 ReAct 模式如何被形式化为可复用的框架组件时，请探索自定义 ReActAgent 实现 。至于所有 Agent 范式背后的基础概念，请回顾 Agent 概念与历史 。
