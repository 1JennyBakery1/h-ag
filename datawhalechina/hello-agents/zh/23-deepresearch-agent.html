    DeepResearch Agent

    20 分钟等级: 高级

    DeepResearch Agent 是一个知识密集型的多 Agent 系统，它实现了深度研究的全生命周期自动化——从主题分解、并行证据收集，一直到结构化报告生成。与 智能旅行助手 中编排确定性 API 工作流的旅行助手不同，该系统直面信息发散性、事实易变性以及来源可引证性需求等挑战。它通过一种TODO 驱动的研究范式来解决这些问题：将复杂的研究主题系统地分解为 3 到 5 个子任务，每个子任务独立研究、总结，随后合成为一份具备完整来源可追溯性的连贯报告。

    来源: Chapter14-Automated-Deep-Research-Agent.md, agent.py

    架构概述

    系统采用经典的前后端分离架构，划分为四个独立的层。Vue3+TypeScript 前端通过服务器发送事件 (SSE) 与 FastAPI 后端通信，后端编排了三个基于 HelloAgents 框架构建的专用 Agent，每个 Agent 均由外部搜索引擎和 LLM 提供商提供支持。

    数据流遵循八步生命周期：用户输入 → 建立 SSE 连接 → FastAPI 接收请求 → 规划阶段将主题分解为子任务 → 执行阶段搜索并总结每个子任务 → 报告阶段整合所有总结 → 流式返回推送进度和结果 → 前端实时渲染。

    来源: Chapter14-Automated-Deep-Research-Agent.md, main.py, agent.py

    TODO 驱动的研究范式

    该系统的核心洞察在于，“研究”并非单一查询，而是一个结构化的过程。TODO 驱动的范式将开放性的研究主题转化为确定性的三阶段流水线：规划 → 执行 → 报告。每个阶段都有专用的 Agent、明确的输入和输出，以及清晰的故障模式。

    阶段一：规划 — 主题分解

    研究规划专家接收研究主题和当前日期，随后将其分解为 3 到 5 个子任务。每个子任务包含三个字段：title（简洁标签）、intent（该子任务的重要性）和 query（优化后的搜索字符串）。规划器使用结构化的 JSON 输出以确保结果可被机器解析：

    规划器的提示词强制要求互补性（避免冗余子任务）、可搜索性（每个查询必须产生可检索的结果）和覆盖度（3-5 项涵盖基础 → 应用 → 趋势）。当 LLM 无法生成有效的 JSON 时，系统会回退到单一的 create_fallback_task，对原始主题发起宽泛的查询。

    PlanningService 中的 _extract_tasks 方法实现了一个多策略 JSON 解析器：它首先尝试定位包含 "tasks" 键的 JSON 对象，然后尝试解析裸 JSON 数组，最后回退到解析 [TOOL_CALL:note:...] 表达式。这种防御性解析至关重要，因为 LLM 的输出格式合规性永远无法得到绝对保证。

    来源: planner.py, prompts.py, Chapter14-Automated-Deep-Research-Agent.md

    阶段二：执行 — 搜索与总结

    对于每个 TODO 项，执行器执行四步流水线：搜索 → 去重 → 总结 → 持久化。dispatch_search 函数将请求路由到配置的后端（DuckDuckGo、Tavily、Perplexity 或 SearXNG），随后 prepare_research_context 根据URL 对来源去重，并将其格式化后提供给总结 Agent。

    任务总结专家接收格式化后的搜索上下文以及笔记协作指导，读取当前笔记状态，将总结写回，并生成带有编号来源引证的 Markdown 输出。关键在于，在流式模式下，总结器使用了 generator + getter 模式——生成器产出可见的文本块（剥离 <think/> token 后），而获取器则为下游消费累积完整的输出。

    来源: agent.py, summarizer.py, search.py

    阶段三：报告 — 整合与综合

    报告撰写专家将所有任务总结整合为一份结构化报告。它通过 NoteTool 读取每个任务的笔记，合并研究发现，并按照五段式模板生成 Markdown 文档：背景概述、核心洞察、证据与数据、风险与挑战以及参考文献。

    ReportingService 中的 strip_tool_calls 后处理步骤至关重要——Agent 可能会在其输出中发出 [TOOL_CALL:note:...] 指令作为笔记协作的一部分，但这些内容绝不能泄露到面向用户的报告中。来自 text_processing.py 的 strip_tool_calls 函数负责处理此类清理工作。

    来源: reporter.py, prompts.py, Chapter14-Automated-Deep-Research-Agent.md

    ToolAwareSimpleAgent 扩展

    这三个 Agent 都是 ToolAwareSimpleAgent 的实例，这是对框架中 SimpleAgent 的扩展，通过 tool_call_listener 回调增加了工具调用可观测性。每次 Agent 调用工具（通常是 NoteTool）时，监听器都会接收到一个包含 agent_name、tool_name、raw_parameters、parsed_parameters 和 result 的载荷。这实现了实时进度跟踪、调试，以及为前端提供 SSE 事件流。

    ToolCallTracker 收集这些事件，从参数或标签中推断 task_id，从工具结果中提取 note_id，并将它们同步回对应的 TodoItem 对象。在流式模式下，它还支持一个事件接收器回调，可以立即将工具事件推送到 SSE 队列，以实现前端实时更新。

    来源: agent.py, tool_events.py, Chapter14-Automated-Deep-Research-Agent.md

    NoteTool 协作协议

    NoteTool 充当 Agent 之间的共享记忆底层基座。每个 Agent 遵循提示词中编码的结构化协作协议：

    1. 规划器为每个子任务创建一个带有 ["deep_research", "task_{id}"] 标签的 task_state 笔记
    2. 总结器在总结前读取该笔记，然后用总结内容更新它
    3. 报告生成器在生成最终报告前读取所有任务笔记，并可选择创建一个 conclusion 笔记

    notes.py 中的 build_note_guidance 函数会根据每个任务的当前状态动态生成精确的 [TOOL_CALL:note:...] 语法——无论笔记已存在（读取 → 更新）还是需要创建（创建 → 记录 note_id）。这确保了 Agent 始终基于最新的笔记状态进行操作，且其修改具备可追溯性。

    来源: notes.py, prompts.py, tool_events.py

    流式架构与并发

    系统提供两种执行模式：同步 (run) 和流式 (run_stream)。流式模式为生产环境路径，支持前端实时进度可视化。

    并发任务执行

    在流式模式下，TODO 项使用 Python 线程并行执行，并采用基于 Queue 的事件路由系统，将来自并发工作线程的结果多路复用到单一的 SSE 流中：

    每个事件都附加了 step（任务索引）和 stream_token（每个任务唯一）信息，以便前端将流式文本块路由到正确的 UI 面板。enqueue 辅助函数会自动从 task_id 解析通道映射，确保在并发执行下事件归属的一致性。

    来源: agent.py, main.py

    前端设计

    Vue3 前端实现了双布局范式：用于主题提交的居中输入卡片，以及用于研究执行的全屏分屏视图。App.vue 组件在本地管理所有状态——todoTasks、progressLogs、reportMarkdown 和 activeTaskId——完全由来自后端的 SSE 事件驱动。

    左侧边栏显示研究主题、选定的搜索引擎、进度条（completedTasks / totalTasks）以及“开始新研究”按钮。右侧面板包含一个状态栏、可折叠的进度日志时间线、带有每个任务状态标签（pending → in_progress → completed/skipped/failed）的任务列表，以及一个渲染带来源引证的流式 Markdown 总结的任务详情视图。最终报告在 final_report SSE 事件到达后，于专用的 Markdown 查看器中渲染。

    搜索引擎下拉列表是动态填充的，允许针对每次请求覆盖后端，该选项将作为 ResearchRequest 载荷中的 search_api 字段传递。

    来源: App.vue, Chapter14-Automated-Deep-Research-Agent.md
