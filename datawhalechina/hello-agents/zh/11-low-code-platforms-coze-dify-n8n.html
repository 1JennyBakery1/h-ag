    低代码平台（Coze、Dify、n8n）

    22 分钟等级: 进阶

    使用 Python 从零开始构建智能体——正如你在前几章中对 ReAct、Plan-and-Solve 和 Reflection 所做的那样——能为你提供对内部机制不可替代的理解。但当工程效率至关重要时，基于平台的开发提供了更高阶的抽象，让你能够专注于智能体思考与行动的逻辑，而非繁琐的样板编排。本页梳理了三大代表性低代码平台——Coze、Dify 和 n8n ——的架构版图，并带你逐个进行动手实践，以便你在真实项目中做出明智的平台决策。

    来源: 第五章 基于低代码平台的智能体搭建.md

    为什么低代码平台如此重要

    “重新发明轮子”对学习而言至关重要，但“站在巨人的肩膀上”对产品交付而言同样不可或缺。当业务逻辑变得复杂时，纯代码的维护成本会呈爆炸式增长。低代码平台同时解决了四个核心痛点：

    价值维度解决的问题具体收益
    降低技术门槛API 调用、状态管理、并发控制非程序员可通过拖拽连接节点构建智能体
    提升开发效率数天的编码 → 数分钟的原型搭建借助可视化工作流编辑器快速验证想法
    提高可观测性终端日志不透明跨节点的端到端数据流可视化
    标准化最佳实践反复重新发现最优模式内置 ReAct 模板、优化的 RAG 引擎、工具调用规范

    核心洞见：低代码平台并非要取代代码——而是提供了一个互补的抽象层。 你可以在平台上进行原型设计并在代码中精炼，或者以可视化方式处理标准流程，同时以编程方式定制边缘场景。

    来源: 第五章 基于低代码平台的智能体搭建.md

    Coze：插件驱动的智能体组装

    架构与功能模块

    由字节跳动开发的 Coze，将智能体开发塑造为一种游戏般的组装过程。其 UI 围绕包含项目开发、资源库、效果评估和空间配置的开发工作区展开。该平台支持三种 Agent 模式——单 Agent 自主规划、单 Agent 对话流和多 Agent——以及独立的 AI 应用。

    捕捉 Coze 设计理念的隐喻：

    游戏组件Coze 对应物在 Agent 中的作用
    关卡路线图Workflow（工作流）定义执行路径
    NPC 对话Dialog Flow（对话流）构建对话结构
    技能卡Plugins（插件）外部能力调用
    百科全书Knowledge Base（知识库）特定领域检索
    快捷物品栏Cards（卡片）快捷组件
    移动按键Prompts（提示词）行为导向
    云存档Database（数据库）持久化状态
    关卡审核员Publishing Management（发布管理）部署关卡
    角色创建Model Management（模型管理）LLM 选择与调优
    评分系统Effect Evaluation（效果评估）质量基准测试

    动手实践：构建“每日 AI 简报”智能体

    本案例演示了 Coze 的插件集成流水线——构建一个自动聚合多个来源的 AI 新闻、学术论文和开源动态的智能体。

    第一步——插件配置。 从 Coze 的插件库中添加 RSS、GitHub 和 Arxiv 插件。每个插件都需要精确的参数调整：

    RSS 链接配置
- 36Kr:    https://www.36kr.com/feed
- Huxiu:   https://rss.huxiu.com/
- IT Home: http://www.ithome.com/rss/
- InfoQ:   https://feed.infoq.com/ai-ml-data-eng/

GitHub 插件配置
- q: AI
- per_page: 10
- sort: updated

Arxiv 插件配置
- count: 5
- search_query: AI
- sort_by: 2

    第二步——结构化提示词设计。 Coze 将提示词分为 System Prompt（长期行为准则）和 User Prompt（带有变量插值如 {{articles}}、{{arxiv}}、{{GitHub}} 的特定任务指令）。系统提示词将智能体设定为资深科技媒体编辑，并强制执行输出格式：带有 emoji 标签的条目、每个条目附带来源链接，以及严格的 AI 主题相关性过滤。

    第三步——测试、调试、发布。 在 Coze 的预览界面中运行智能体，验证内容准确性和格式合规性，然后一键发布到微信、飞书、抖音等平台。

    Coze 的优势与局限

    优势局限
    丰富的插件生态，支持拖拽式组装不支持 MCP 协议（已在路线图中）
    直观的可视化工作流编排高级插件配置需要技术背景
    灵活的提示词控制与模板管理无可移植的 JSON 导出（仅限 ZIP，付费层级）
    一键多平台部署复杂工作流需要 JS/Python 基础

    Dify：开源全栈智能体平台

    架构与生态

    Dify 将 Backend-as-a-Service (BaaS) 和 LLMOps 融合为分层的模块化架构——数据层、开发层、编排层和基础设施层——各层解耦以实现独立扩展。它具备模型中立性：任何 OpenAI 兼容的 LLM（GPT、Deepseek、Llama 等）都可以通过简单配置接入。

    Dify Marketplace 是该平台的增长引擎，托管了跨越五大类别的 8,600 多个插件：

    类别用途示例插件
    ModelsLLM 供应商集成Azure OpenAI, 本地模型
    Tools外部服务调用Google Search, Notion, DuckDuckGo
    Agent Strategies推理模式选择ReAct, function-calling 策略
    Extensions平台能力增强自定义中间件
    Bundles策划的插件包特定领域的入门套件

    Dify 同时支持 SaaS 云端和自托管部署（Docker Compose 一键启动），使其适用于对数据敏感的企业环境。

    动手实践：构建超级 Agent 个人助手

    本案例构建了一个多模块 Chatflow 智能体，它通过问题分类器将用户查询路由到专门的子 Agent——这种模式映射了传统软件工程中的微服务架构。

    MCP 集成（关键路径）。 Dify 的 MCP 支持采用 SSE 模式进行稳定的流式通信。配置流程如下：

    1. 导航到 ModelScope 的 MCP 市场，选择托管的 MCP 服务（例如，Amap/高德地图）
    2. 复制 SSE 端点 URL，去掉 mcp-server 前缀
    3. 在 Dify 的 Agent 节点中，选择 ReAct 策略，添加 MCP 工具，并粘贴配置
    4. 将“获取时间戳”等工具与 MCP 服务一起包含，以实现具备时间感知的推理

    问题分类器 → 专门的子 Agent 模式对于生产级智能体至关重要。单一庞大的 LLM 处理所有任务会遭受任务干扰——数据分析的提示词指令会降低创意写作的质量，反之亦然。分类优先的路由在提示词层面实现了关注点分离。

    如需包含截图的完整分步演练，请参阅专属教程：Dify智能体创建保姆级操作流程。

    n8n：工作流自动化与 AI Agent 的结合

    核心心智模型：节点与工作流

    n8n 本质上是一个工作流自动化平台，它集成了 AI 能力——而不是原生的 LLM 应用构建器。这一区别至关重要：在 n8n 中，LLM 是更大自动化流水线中众多节点之一，而非宇宙的中心。

    两个基础概念：

    • 节点：原子执行单元。n8n 提供了 400 多个预构建节点，涵盖电子邮件、数据库、API、文件处理，以及现在的 AI 操作。节点分为触发节点（工作流启动器——“收到新 Gmail”、“定时触发”、“Webhook 触发”）和常规节点（数据处理器——“读取 Google Sheets”、“调用 OpenAI”、“插入数据库”）。
    • 工作流：连接节点的有向图。数据以结构化 JSON 的形式在节点之间流动。一个触发节点，N 个常规节点，支持分支与合并。

    动手实践：构建智能邮件 Agent

    本案例展示了 n8n 的独特价值主张——将 AI Agent 嵌入真实业务自动化流程中。架构遵循：接收 → AI Agent（思考 → 决策 → 工具调用） → 回复。

    第一步——准备 Agent 的记忆。 一个独立的工作流将私有知识加载到内存向量存储中：

    运行此工作流一次。Simple Vector Store 使用 Memory Key: my-dailytime——这相当于数据库表名，Agent 稍后将对其进行查询。

    第二步——构建 Agent 主流程。 AI Agent 节点是 n8n 的“单节点编排器”——它将 LLM、Memory 和 Tools 绑定到一个配置点：

    组件配置目的
    Chat ModelGoogle Gemini Chat Model推理核心
    MemorySimple Memory（按 threadId 索引）每个邮件线程的对话连续性
    Tool 1SerpAPI网络搜索以回答问题
    Tool 2Simple Vector Store（检索模式，相同的 Memory Key + 相同的 Embeddings 模型）访问私有知识

    Agent 的 System Prompt 编码了一个条件逻辑管道：使用 SerpAPI 回答发件人的问题，使用 Vector Store 检查工作时间，然后根据时间比较前置状态前缀（非工作时间通知或简单问候）。输出被强制为包含 shouldReply、subject 和 body 字段的严格 JSON。

    第三步——发送回复。 将 Agent 输出连接到 Gmail Send 节点，使用 n8n 表达式映射 JSON 字段：

    To:      {{ $('Gmail').item.json.From }}
Subject: Re: {{ $('Gmail').item.json.Subject }}
Message: {{ $json.output }}

    n8n 的优势与局限

    维度优势局限
    开发效率可视化工作流——端到端可见数据流调试复杂流程需要逐节点检查；无断点功能
    集成400+ 服务节点 + 统一的 AI Agent 节点内存存储（Simple Memory、Simple Vector Store）在重启时丢失数据
    部署通过 Docker 自托管；最简单的全功能私有 Agent 方案版本控制不如基于 Git 的代码成熟；协同编辑受限
    性能在中低并发下对企业自动化表现出色与纯代码相比，在极高并发下存在节点调度开销

    平台选择决策框架

    基于上述三个动手实践案例，以下是一个基于项目约束的决策框架：

    场景推荐平台理由
    C 端聊天机器人，1 名产品经理 + 1 名前端开发，预算紧张Coze零代码，上线最快
    企业合同审核，私有数据，OA 集成Dify自托管，RAG，企业级安全，MCP
    内部开发效能工具（代码审查、Bug 追踪、CI 同步）n8n跨开发工具链的工作流自动化
    混合需求的原型 → 生产混合方案在 Coze 上验证，在 Dify 上构建生产，用 n8n 自动化

    核心要点：低代码平台与代码并非互斥。 最有效的团队将平台用于标准化流程，将代码用于定制逻辑——并根据手头的问题灵活切换。
