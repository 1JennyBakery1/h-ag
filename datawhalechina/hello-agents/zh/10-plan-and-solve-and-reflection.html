    计划与求解及反思

    24 分钟等级: 进阶

    除了 ReAct 逐步响应的推理方式，智能体还可以针对复杂任务采取更加深思熟虑的策略。本页探讨了两种强大的范式：Plan-and-Solve（计划与解决） 将战略规划与战术执行分离；Reflection（反思） 则为智能体赋予了自我批判与迭代优化的能力。二者共同代表了智能体从单纯的“行动与反应”向“提前规划”和“从自身错误中学习”的转变。

    来源：[第四章 智能体经典范式构建.md](/docs/chapter4/第四章 智能体经典范式构建.md#L350-L365)

    从响应到深思：为什么 ReAct 并非总是足够

    在 ReAct 模式实现 中，我们看到了 Thought→Action→Observation（思考→行动→观察）循环如何实现动态的、环境驱动的推理。然而，ReAct 的优势——对每个新观察的响应能力——也是其致命弱点。缺乏全局计划，智能体可能会偏航：它可能追踪无关线索、循环回到已探索的路径，或者在多步骤任务中迷失原始目标。这正是 Plan-and-Solve 和 Reflection 登场的原因，它们各自解决了 ReAct 局限性的不同维度。

    ReAct 的局限性解决该局限的范式核心机制
    无全局计划；决策纯粹是局部的Plan-and-Solve预先分解问题，然后逐步执行计划
    除外部工具反馈外无自我纠错能力Reflection评估并优化智能体自身输出的内部批判循环
    在长链推理中容易产生“思维漂移”Plan-and-Solve结构化的计划使执行保持在正轨上
    初始输出质量可能欠佳Reflection通过 Execute→Reflect→Refine（执行→反思→优化）循环进行迭代优化

    来源：[第四章 智能体经典范式构建.md](/docs/chapter4/第四章 智能体经典范式构建.md#L500-L530)

    Plan-and-Solve：先思考，后行动

    Plan-and-Solve 提示词由 Lei Wang 于 2023 年提出，诞生于一个精准的观察：Chain-of-Thought（思维链）推理在处理多步骤复杂问题时经常“脱轨”。解决方案出奇地简单——将规划与执行解耦。如果说 ReAct 是按部就班追踪线索的侦探，那么 Plan-and-Solve 就是在砌第一块砖之前先绘制出完整蓝图的设计师。

    两阶段架构

    该范式在两个严格分离的阶段中运作，通过一个结构化的计划对象连接：

    形式化地说，规划模型 π_plan 根据原始问题 q 生成有序计划 P = (p₁, p₂, …, pₙ)。随后，在解决阶段，执行模型 π_solve 按顺序处理每个步骤，其中步骤 i 的解取决于问题、完整计划以及所有先前结果：

    • 计划生成：P = π_plan(q)
    • 步骤执行：sᵢ = π_solve(q, P, (s₁, …, sᵢ₋₁))

    这种分离确保了每个执行步骤都锚定于全局一致的策略，而非短视地做出决定。

    来源：[第四章 智能体经典范式构建.md](/docs/chapter4/第四章 智能体经典范式构建.md#L530-L570)

        self.llm_client = llm_client

    def plan(self, question: str) -> list[str]:

        messages = [{"role": "user", "content": prompt}]
        response_text = self.llm_client.think(messages=messages) or ""
        try:
            plan_str = response_text.split("```python")[1].split("```")[0].strip()

            return plan if isinstance(plan, list) else []

            return []

    Plan-and-Solve 实战演示

    考虑以下推理任务："一家水果店周一卖出了 15 个苹果。周二的销量是周一的两倍。周三的销量比周二少 5 个。这三天总共卖出了多少个苹果？"

    规划器将其分解为四个原子步骤：

    步骤 1: "计算周一卖出的苹果数量：15个"       → 结果: 15
步骤 2: "计算周二卖出的苹果数量：15 × 2 = 30" → 结果: 30
步骤 3: "计算周三卖出的苹果数量：30 - 5 = 25"  → 结果: 25
步骤 4: "计算三天总销量：15 + 30 + 25 = 70"    → 结果: 70

    每个步骤的结果通过历史记录字符串流入下一步，确保了逻辑连贯性。最终答案 70 从最后一步得出——这是结构化顺序执行的直接结果。

    来源：[第四章 智能体经典范式构建.md](/docs/chapter4/第四章 智能体经典范式构建.md#L780-L830)

    优势、局限与静态计划问题

    Plan-and-Solve 在结构清晰度和目标一致性方面表现出色——一旦计划制定，每个执行步骤都有了明确的目的。然而，其决定性特征也是其最大限制：计划是静态的。如果步骤 3 发现步骤 1 的假设是错误的，智能体没有内置机制来回顾和修改计划。这就是“静态计划问题”，它与 ReAct 的动态适应性形成了直接对比。

    方面优势风险
    预先规划全局一致性；无“思维漂移”计划可能基于错误的假设
    顺序执行状态流转清晰；易于调试无法适应意外的中间结果
    结构化输出机器可解析的计划；可组合若 LLM 未遵循输出格式则易出错
    无工具依赖适用于纯推理；无需外部 API无法整合实时的外部信息

    为了在实践中缓解静态计划问题，可以考虑添加“重新规划触发器”——如果执行步骤产生的结果与计划的假设相矛盾，则带上累积的上下文再次调用规划器以生成修订后的计划。这种混合方法结合了 Plan-and-Solve 的结构性与 ReAct 的适应性。

    来源：[第四章 智能体经典范式构建.md](/docs/chapter4/第四章 智能体经典范式构建.md#L830-L870)

    Reflection：自我批判的力量

    虽然 Plan-and-Solve 解决了 ReAct 在规划上的缺失，但它与 ReAct 和 Plan-and-Solve 都有一个根本的共同局限：一旦产生输出，智能体就认为任务完成了。Reflection（受 Shinn, Noah 的 Reflexion 框架，2023 年启发）引入了一种质的不同的能力——智能体可以通过内部批判循环来评估并迭代改进自身的工作。

    Execute-Reflect-Refine 循环

    Reflection 作为一个可重复直至收敛的迭代三阶段循环运作：

    形式化地说，在迭代 i 中，反思模型 π_reflect 检查当前输出 Oᵢ 并生成结构化反馈 Fᵢ。然后，优化模型 π_refine 结合先前的输出和反馈生成改进后的输出 Oᵢ₊₁：

    • 反馈生成：Fᵢ = π_reflect(Task, Oᵢ)
    • 输出优化：Oᵢ₊₁ = π_refine(Task, Oᵢ, Fᵢ)

    此循环会一直持续，直到反思者声明“无需改进”或达到最大迭代次数。

    来源：[第四章 智能体经典范式构建.md](/docs/chapter4/第四章 智能体经典范式构建.md#L870-L920)

    记忆模块：实现跨周期的迭代

    Reflection 本质上是迭代的，而迭代需要记忆。Memory 类充当短期情景存储，记录了执行和反思的完整轨迹，使智能体能够“记住它尝试了什么以及学到了什么”。

    get_trajectory 方法将整个执行-反思历史序列化为可注入提示词的单一文本块。get_last_execution 方法则提供了对最新输出的快速访问，供反思者进行批判。

    来源：Reflection.py, [第四章 智能体经典范式构建.md](/docs/chapter4/第四章 智能体经典范式构建.md#L920-L970)

    三个提示词，三种角色

    Reflection 的力量源于在各个阶段为 LLM 分配不同的角色设定，每个角色都有其独特的目标和评估标准：

    阶段提示词角色目标关键设计原则
    Execute“高级 Python 程序员”生成初始解决方案直接输出；不自我怀疑
    Reflect“极其严格的代码评审员与算法工程师”批判效率瓶颈专注于算法层面的改进，而非代码风格
    Refine“高级 Python 程序员（修订版）”应用反馈生成改进代码必须纳入所有反馈点

    反思者的提示词是刻意带有对抗性的——它指示模型专注于算法效率，因为毫无重点的批判（“代码可以更好”）会产生无法操作的反馈。反思提示词中的特异性直接决定了优化的质量：

    REFLECT_PROMPT_TEMPLATE = """
你是一位极其严格的代码评审专家和资深算法工程师，对代码的性能有极致的要求。
你的任务是审查以下Python代码，并专注于找出其在**算法效率**上的主要瓶颈。
...
如果存在，请清晰地指出当前算法的不足，并提出具体的、可行的改进算法建议。
如果代码在算法层面已经达到最优，才能回答"无需改进"。
"""

    收敛标准——在反馈中检查“无需改进”——提供了一个自然的终止信号，这比简单的迭代计数器在语义上更具意义。

    Reflection 实战：从试除法到筛法

    当面临任务*“编写一个 Python 函数，找出 1 到 n 之间的所有素数”*时，Reflection 智能体在迭代中展示了显著的质量提升：

    第 0 次迭代 — 初始执行：智能体生成了一种时间复杂度为 O(n × √n) 的直观试除法方法。它运行正确，但对于大规模输入效率低下。

    第 1 次迭代 — 反思：严格的评审员指出了瓶颈：“每个数都需要进行试除法检查，这导致了较高的时间开销”。它推荐了时间复杂度为 O(n log log n) 的埃拉托斯特尼筛法。

    第 1 次迭代 — 优化：智能体实现了筛法，实现了显著的渐进性能提升。

    第 2 次迭代 — 反思：评审员承认筛法已经非常高效，提及了针对特殊场景的高级替代方案（分段筛法、仅处理奇数的筛法），但得出结论：对于一般使用“无需改进”。循环终止。

    这一轨迹展示了 Reflection 的标志性特征：它推动了解决方案质量的质的飞跃，而不仅仅是渐进的错误修复。智能体从完全不同的算法类别（试除法 → 筛法）进行了转换，这是简单的“修复错误”提示词永远无法实现的。

    来源：[第四章 智能体经典范式构建.md](/docs/chapter4/第四章 智能体经典范式构建.md#L1090-L1150)

    成本效益分析：Reflection 何时值得

    Reflection 是一种“以成本换取质量”的策略。理解其经济学原理对于做出合理的架构决策至关重要。

    维度成本效益
    API 调用N 次迭代至少需要 2N+1 次调用（1 次初始 + N×2 次反思+优化）输出质量随每次迭代而提升
    延迟串行过程；每次迭代需等待上一次完成能够捕获单次通过方法遗漏的逻辑错误和次优策略
    提示词工程需要设计、测试和维护三个不同的提示词模板结构化的角色设定能产生有针对性、可操作的反馈
    复杂性记忆模块 + 收敛逻辑 + 多角色编排独立于外部工具的内部自我纠错循环

    适用 Reflection 的场景：生成关键业务代码、撰写要求准确性的技术报告、错误代价高昂的科学推理，或任何质量优先于速度的场景。避免使用 Reflection 的场景：需要实时响应、“足够好”的答案即可满足，或 API 成本预算紧张。

    来源：[第四章 智能体经典范式构建.md](/docs/chapter4/第四章 智能体经典范式构建.md#L1150-L1200)

    范式对比：选择合适的架构

    这三种经典范式代表了组织智能体“思考”和“行动”的根本不同策略：

    标准ReActPlan-and-SolveReflection
    规划无（短视）静态的预先计划无（但可自我纠错）
    适应性高（对观察做出反应）低（计划固定）中（通过自我批判适应）
    自我纠错仅通过外部工具反馈无内部批判循环
    每任务 LLM 调用可变（循环直至完成）1（计划）+ N 步1 + 2×迭代次数
    最适用于需要实时外部信息的任务结构化的、可分解的推理质量至上的生成任务
    关键风险思维漂移；局部最优计划过时；无错误恢复成本攀升；收益递减

    组合范式：走向混合架构

    这些范式并非互斥的。在实践中，最健壮的智能体会结合它们的优势：

    • Plan-and-Solve + ReAct：使用 Plan-and-Solve 制定高级策略，但当个别执行步骤遇到需要外部信息的子问题时，允许其使用 ReAct 风格的工具调用。
    • ReAct + Reflection：在 ReAct 智能体生成最终答案后，运行一个 Reflection 循环来批判和改进完整的推理轨迹。
    • Plan-and-Solve + Reflection：生成计划，执行它，然后对整个执行轨迹进行反思——如果反思揭示了系统性问题，则可能重新规划。

    范式或其组合的选择应由任务的核心需求驱动：它是否需要外部信息（→ ReAct）、结构化分解（→ Plan-and-Solve），还是高质量输出（→ Reflection）？大多数现实世界的任务都能从这三者的元素中受益。
