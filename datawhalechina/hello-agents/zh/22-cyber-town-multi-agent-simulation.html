    赛博小镇多 Agent 模拟

    24 分钟等级: 高级

    赛博小镇多智能体模拟是一个里程碑式项目，它将大语言模型 Agent 与实时游戏引擎相融合，构建出一个交互式的 2D 像素风办公环境，其中的 AI 驱动 NPC 拥有持久记忆、不断演进的关系网以及自主行为。与传统的对话树 NPC 不同，赛博小镇的每位居民都由 HelloAgents 框架中独立的 SimpleAgent 实例提供支持——具备语义记忆检索、情感驱动的好感度更新以及批量生成的环境对话能力。本页将深入剖析完整的架构、数据流和实现模式，旨在帮助希望理解、扩展或重构该系统的开发者。

    系统架构

    赛博小镇采用解耦的游戏引擎 + 后端服务架构，划分为四个截然不同的层级：Godot 4 渲染前端、FastAPI 编排后端、HelloAgents NPC 智能层，以及用于记忆和关系状态的持久化数据层。这种分离意味着前端对 LLM 内部机制完全透明——它仅通过 REST 端点进行通信，从而可以轻松独立地替换游戏引擎或 Agent 框架。

    前端层使用 Godot 4.x 渲染 Datawhale 办公室场景，处理玩家移动（WASD），并触发 NPC 交互（E 键）。当玩家发起对话时，Godot 的 api_client.gd 会向 /chat 发送 HTTP POST 请求；至于 NPC 的环境行为，则通过轮询 /npcs/status 端点，该端点会同时返回所有 NPC 批量生成的一句台词。后端的 NPCAgentManager 编排每个 NPC 的 SimpleAgent 实例，每个实例都连接着自身的 MemoryManager，并受 RelationshipManager 的好感度上下文影响。NPCStateManager 运行一个 asyncio 循环，每 30 秒调用一次 NPCBatchGenerator，在单次 LLM 调用中为所有 NPC 生成符合语境的环境对话——这将 API 成本降低至逐个 NPC 调用的三分之一。

    来源: Chapter15-Building-Cyber-Town.md, main.py, state_manager.py

    NPC Agent 系统

    Agent 创建与角色配置

    每个 NPC 都被实例化为一个 SimpleAgent 实例，并拥有精心设计的系统提示词，该提示词编码了角色身份、性格、专长、说话风格、爱好和行为约束。agents.py 中的 NPC_ROLES 字典是所有 NPC 定义的唯一事实来源——三个角色占据了 Datawhale 办公室中不同的职业领域。

    NPC角色位置核心活动性格特征
    张三Python 工程师工位区写代码严谨，技术黑话，偶尔吐槽 Bug
    李四产品经理会议室整理需求外向，用户导向，善用比喻
    王五UI 设计师休息区喝咖啡审美在线，温和，表达艺术化

    每个 NPC 的系统提示词遵循结构化模板，以确保角色一致性。它包含明确的行为准则——使用第一人称，将回复控制在 30-50 字以内，保持专业语调，在问题超出专长时推荐其他同事，最关键的是，绝不通过声称自己是 AI 来打破角色设定。这不仅仅是提示词工程的技巧；它是一项架构契约，下游的记忆和好感度系统依赖它来实现连贯的状态演进。

    NPCAgentManager 是一个单例编排器，它在启动时初始化所有 Agent，为每个 NPC 创建记忆管理器，并接入 RelationshipManager。它暴露了 chat() 作为主要入口点——FastAPI 的 /chat 端点会委托给该方法。

    来源: agents.py

    对话处理流水线

    当玩家向 NPC 发送消息时，chat() 方法会执行一个六阶段的流水线，将记忆检索、好感度上下文注入、LLM 生成、好感度分析和记忆持久化交织在一起。这条流水线是系统的架构核心——其中的每一个设计决策都服务于一个目标：让 NPC 感觉像是在记住并且在乎。

    该流水线的核心洞察在于生成前进行上下文丰富。Agent 绝不会收到原始的玩家消息——它收到的是一个复合提示词，包含当前的好感度等级（这决定了语气，从低好感度的“冷淡疏离”到高好感度的“非常热情友好”）、通过语义搜索检索到的相关历史记忆，以及实际的玩家消息。这意味着，一个被多次侮辱的 NPC 会简短而冷淡地回应，而一个受到赞美的 NPC 则会热情而坦诚。

    增强提示词模式——在 LLM 调用之前注入好感度状态和记忆上下文，而非进行后处理——正是赛博小镇 NPC 在跨会话中保持连贯性的秘诀。如果你扩展此系统，请抵制将关系影响作为生成后编辑来处理的诱惑；LLM 必须看到关系状态，才能真实地调节其输出。

    来源: agents.py

    记忆系统

    每个 NPC 运行着由 HelloAgents MemoryManager 支持的双通道记忆架构：用于短期对话上下文的 WorkingMemory 和用于长期语义检索的 EpisodicMemory。这反映了认知科学中对工作记忆（你正在积极思考的内容）和情景记忆（你在被提示时能回忆起的内容）的区分。

    属性WorkingMemoryEpisodicMemory
    用途维持对话连贯性检索相关的历史对话
    容量10 条消息100 条记录
    Token 预算2,000 tokens向量库索引
    持久性易失性 (TTL: 120 分钟)持久化 (SQLite 支持)
    检索方式顺序检索 (最近优先)语义搜索 (top-k)
    遗忘机制TTL 过期重要性阈值 (0.3)

    记忆在 Agent 初始化期间按 NPC 进行配置，每个 NPC 在 memory_data/ 下拥有自己的存储目录：

    每次对话交流都会以丰富的元数据被持久化——说话者身份、时间戳、当前好感度分数、好感度变化增量以及情感标签。这些元数据不仅是日志记录；它还支持未来的扩展，比如“记住你给他们带来何种感受的 NPC”或跨会话的关系连续性。

    来源: agents.py, MEMORY_SYSTEM_GUIDE.md

    好感度（关系）系统

    好感度系统是将赛博小镇从一群聊天机器人转变为社交模拟的关键。每个 NPC 对每位玩家都维护着一个数值化的好感度分数（0–100），该分数直接调节 NPC 的对话语气、分享意愿和互动深度。该系统由基于 LLM 的情感分析器驱动，评估每一次对话交流。

    好感度等级与行为修正

    分数范围等级行为修正
    80–100挚友"非常热情友好,像老朋友一样亲切,愿意分享私人话题"
    60–79亲密"友好热情,愿意多聊,会主动关心对方"
    40–59友好"礼貌友善,正常交流,保持专业" (默认初始状态)
    20–39熟悉"礼貌但略显生疏,回答简洁"
    0–19陌生"冷淡疏离,不太愿意多说,回答简短"

    所有 NPC 初始好感度为 50.0（友好），确保了一个中立但易于接纳的起点。修正字符串在每次 LLM 调用之前被直接注入到系统提示词上下文中，因此 LLM 能够原生地根据关系状态调整其输出风格。

    基于 LLM 的情感分析

    RelationshipManager 使用了一个名为 "AffinityAnalyzer" 的专用 SimpleAgent，其系统提示词经过精心设计，定义了情感评分规则。对于每一次玩家与 NPC 的交流，分析器接收双方消息并返回结构化的 JSON 裁定：

    评分规则在分析器提示词中进行了明确校准：

    交互类型好感度变化量
    赞美、感激、寻求建议+3 到 +8
    友好问候、正常交流+1 到 +3
    普通闲聊、中性话题0
    批评、质疑、不耐烦-3 到 -8
    侮辱、攻击、恶意-8 到 -15

    好感度分析器对每次对话交流使用单独的 LLM 调用，这会增加延迟和成本。对于生产部署，考虑用轻量级情感分类器（例如，微调的 DistilBERT）替换基于 LLM 的分析器来处理常见情况，仅在情感模糊时上报给 LLM。_parse_analysis() 中的 JSON 解析已经包含了对格式错误的 LLM 输出的健壮回退处理——将此模式扩展到混合分类器/LLM 流水线是直截了当的。

    来源: relationship_manager.py, AFFINITY_SYSTEM_GUIDE.md

    批量对话生成

    赛博小镇中最具实用性的架构决策之一是批量对话生成系统。NPCBatchGenerator 没有为每个 NPC 的环境行为分别发起 LLM 调用，而是构建了一个单一的提示词，同时请求所有 NPC 的对话，解析 JSON 响应，并分发结果。这将 API 成本降至三分之一，并产生了上下文相关的对话——如果张三在调试代码，李四可能会提到帮忙。

    批量提示词是上下文感知的：_get_current_context() 将当前小时映射到六种场景描述之一（清晨到达、专注上午工作、午休、下午苦干、傍晚收尾、深夜加班）之一。当 LLM 不可用时，系统会优雅地回退到存储在 preset_dialogues 中基于时间段的预设对话。

    NPCStateManager 将此生成器封装在一个每 30 秒自动刷新的 asyncio 任务中。Godot 轮询 /npcs/status 端点以获取最新的批量对话，并将其作为 NPC 环境语音气泡或状态文本显示。

    来源: batch_generator.py, state_manager.py

    API 接口

    FastAPI 后端暴露了一个 RESTful API，作为 Godot 前端和 Agent 智能层之间的唯一契约。所有端点均使用 Pydantic 模型编写文档，并可通过 /docs 的 Swagger UI 访问。

    方法端点用途请求体响应
    POST/chat玩家 ↔ NPC 对话{npc_name, message}{npc_name, npc_title, message, success}
    GET/npcs列出所有 NPC—{npcs: [{name, title, location, activity, available}], total}
    GET/npcs/status批量获取 NPC 环境状态—{dialogues: {name: text}, last_update, next_update_in}
    POST/npcs/status/refresh强制批量刷新—{message, dialogues}
    GET/npcs/{name}单个 NPC 详情—NPC 信息 + current_dialogue
    GET/npcs/{name}/memories检查 NPC 记忆?limit=N{npc_name, memories, total}
    DELETE/npcs/{name}/memories清除 NPC 记忆?memory_type=working|episodic确认消息
    GET/npcs/{name}/affinity获取好感度分数?player_id={affinity, level, modifier}
    PUT/npcs/{name}/affinity设置好感度 (测试用)?affinity=N&player_id=确认 + 更新信息
    GET/affinities所有 NPC 好感度?player_id={player_id, affinities: {name: {affinity, level, modifier}}}

    Pydantic 模型强制执行严格类型，并为 Swagger 文档提供示例负载。ChatRequest 需要 npc_name 和 message；ChatResponse 增加了 npc_title、success 标志和 timestamp。NPCStatusResponse 模型携带批量对话字典以及 Godot 客户端用于轮询节奏的时间元数据。

    来源: main.py, models.py

    架构模式与扩展点

    赛博小镇体现了几个值得任何构建多智能体模拟的人研究的设计模式：

    带懒初始化的单例管理器。 NPCAgentManager 和 NPCStateManager 都使用模块级单例获取器（get_npc_manager()、get_state_manager()），在首次访问时进行懒初始化。这避免了导入时的全局状态，同时确保了 FastAPI 进程中的单例实例。

    优雅降级。 每个依赖 LLM 的组件都会检查 self.llm is not None，并回退到预设数据或模拟模式。当 LLM 不可用时，NPCBatchGenerator 返回基于时间的预设对话；NPCAgentManager.chat() 返回符合角色的静态消息。这使得整个系统在没有 API 密钥的情况下也可测试。

    上下文提示词组合。 对话流水线并非使用单一庞大的系统提示词，而是增量地组合上下文——先是好感度上下文，然后是记忆上下文，最后是玩家消息。这种模块化方法使得每个上下文来源都可以独立测试和替换。

    批量与个体混合模式。 系统对 NPC 环境行为使用批量生成（低风险、周期性、一次性全部），而对玩家发起的对话使用单独的 Agent 调用（高风险、按需、按 NPC）。这种混合模式在成本和质量之间取得了平衡——环境对话不需要按 NPC 的记忆上下文，但玩家对话绝对需要。

    富含元数据的记忆存储。 对话保存时附带了好感度分数、好感度变化增量和情感标签作为元数据。这支持了未来的功能，比如“提及关系如何演变的 NPC”或将会话主题与关系轨迹相关联的分析仪表板。

    潜在的扩展方向包括：添加 NPC 间对话（当玩家不在场时 NPC 之间互相交谈），实现 enable_semantic=True 记忆通道以实现类知识图谱的世界理解，用本地分类器替换基于 LLM 的好感度分析器以降低成本，以及通过 API 动态配置角色以扩展到更多 NPC，而非硬编码 NPC_ROLES。

    来源: agents.py, batch_generator.py, relationship_manager.py
