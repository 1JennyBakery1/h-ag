    从零构建自定义 Agent 框架

    23 分钟等级: 高级

    本页面向高级开发者深入介绍 HelloAgents 的架构、设计原理及动手实践——这是一个完全基于第一性原理构建的轻量级、教学导向的 Agent 框架。生产级框架往往以牺牲透明度为代价来优先保证通用性，HelloAgents 则反其道而行之：每一层抽象都有其意图，每一层结构均可检视，每一个组件都将由你亲手构建。该框架随着章节的推进迭代演进，确保你的理解能与代码库同步深化。

    来源: Chapter7-Building-Your-Agent-Framework.md, 第七章 构建你的Agent框架.md

    为什么要构建你自己的框架

    Agent 生态中已充斥着各类成熟的框架——LangGraph、AutoGen、AgentScope——然而从零开始构建依然是一个深思熟虑且极具价值的选择。其动机并非“非我所创”综合征（NIH syndrome），而是基于这样一种认知：只知消费框架而不理解框架，只会造就脆弱的专业技能。当前领域存在的三个结构性问题充分印证了这一点。

    过度抽象导致的复杂性。 通用框架必须服务于所有用例，这催生了层层叠叠的抽象。例如，LangChain 的链式调用机制要求开发者在完成哪怕一项简单任务之前，都必须理解 Chain、Agent、Tool、Memory、Retriever 及其相互关系。学习曲线陡峭并非因为领域本身复杂，而是因为抽象过早。

    API 不稳定性。 商业框架为了抢占市场份额而激进迭代。次版本号之间出现破坏性变更已是家常便饭，开发者发现自己被迫走上了并未主动选择的迁移之路。当框架本身是一个黑盒时，版本升级就成了盲目的信仰之举，而非理性的工程决策。

    内部机制不透明。 当核心逻辑被封装在装饰器链和元类注册表之后，调试就意味着必须阅读框架源码——而这恰恰是使用框架本应避免的状况。定制化变成了修修补补，而修补最终演变为代码分叉。

    构建 HelloAgents 是从框架消费者向框架架构师的转变。你将获得对每一行代码的完全掌控，培养出可迁移至任何框架的系统设计判断力，并产出一个意图与实现之间的距离仅用个位数函数调用即可衡量的代码库。

    来源: Chapter7-Building-Your-Agent-Framework.md, 第七章 构建你的Agent框架.md

    设计理念

    HelloAgents 遵循四大设计原则，在易学与实用之间取得了完美平衡。

    轻量且教学友好。 核心代码按章节分离。任何具备一定 Python 基础的开发者，都能在一次专注的阅读中理解整个框架。依赖极简——仅用 Pydantic 做验证，用 OpenAI 作 API 客户端——别无他物。

    标准 API 实用主义。 OpenAI 的 Chat Completion API 已成为事实标准；所有主流提供商（ModelScope、智谱 AI、Groq）均提供兼容 OpenAI 的端点。HelloAgents 基于此标准构建，而非另起炉灶发明自己的抽象。理解了 HelloAgents，你就理解了行业的通用语言。

    渐进式学习路径。 每一章的代码都通过 pip install "hello-agents==0.1.1" 保存为可安装的历史版本。你可以先体验功能，再动手实现，最后对照参考测试套件进行验证。学习顺序为：体验 → 实现 → 验证。

    统一的工具抽象。 这是架构的基石：除了核心 Agent 类之外，一切皆为 Tool。Memory、RAG、MCP 协议适配器——统统作为工具注册到 ToolRegistry 中。这消除了学习不同子系统的必要性，并确保添加新能力始终是同一操作：registry.register_tool(tool)。

    来源: Chapter7-Building-Your-Agent-Framework.md, 第七章 构建你的Agent框架.md

    核心层：基础组件

    HelloAgentsLLM — 多提供商 LLM 接口

    HelloAgentsLLM 类是框架与语言模型通信的枢纽。它在第 4 章基础客户端之上扩展了三大关键能力：多提供商切换、本地模型集成和提供商自动检测。

    多提供商支持通过基于继承的扩展模式实现，无需修改已安装库的源代码。你只需创建一个子类，重写 __init__ 以拦截自定义提供商，然后通过 super().__init__() 将其余情况委托给父类处理：

    这种模式在架构上意义重大：它确保了你的定制化逻辑能在库升级后幸存，并保持了扩展边界的整洁。

    本地模型集成利用了 VLLM 和 Ollama 均暴露兼容 OpenAI 端点这一事实。无需适配器代码——只需将 base_url 指向本地服务即可：

    提供商默认端点连接模式
    OpenAIhttps://api.openai.com/v1云端 API 密钥
    ModelScopehttps://api-inference.modelscope.cn/v1/云端 API 密钥
    智谱 AIhttps://open.bigmodel.cn/api/paas/v4/云端 API 密钥
    VLLMhttp://localhost:8000/v1本地，无需真实密钥
    Ollamahttp://localhost:11434/v1本地，无需真实密钥

    自动检测由两个协同方法处理。_auto_detect_provider 通过优先级级联解析提供商身份：(1) 提供商特定的环境变量 → (2) base_url 域名/端口匹配 → (3) API 密钥格式启发式判断 → (4) 降级回退至 "auto"。一旦识别出提供商，_resolve_credentials 便会将其映射到正确的默认参数：

    实际效果：用户只需在 .env 中配置 LLM_BASE_URL="http://localhost:11434/v1" 和 LLM_MODEL_ID="llama3"，即可在零附加参数的情况下实例化 HelloAgentsLLM()——框架会自动推断一切。

    自动检测的优先级级联是有意为之——提供商特定的环境变量优先级高于通用变量。这意味着 MODELSCOPE_API_KEY 的优先级高于 LLM_API_KEY，从而避免在存在多个密钥时产生配置歧义。

    实现层：Agent 范式

    在核心层就绪之后，四种 Agent 范式就成了聚焦于具体实现的类，它们继承了基础设施，仅在执行策略上有所不同。下表总结了它们在架构上的权衡：

    Agent执行模型工具集成迭代控制主要用例
    SimpleAgent单次执行 + 可选工具循环可选，通过 [TOOL_CALL] 标记max_tool_iterations通用对话，简单任务
    ReActAgent思考-行动-观察循环强制，通过 ToolRegistrymax_steps需使用工具的多步推理
    ReflectionAgent生成 → 反思 → 优化循环无（自包含）max_reflections通过自我批评提升质量
    PlanAndSolveAgent计划分解 → 顺序执行每步可选计划长度复杂的多步骤问题

    SimpleAgent — 带可选工具的对话基础

    SimpleAgent 展示了框架中最精简的可用 Agent：它构建消息列表（系统提示词 + 历史记录 + 当前输入），调用 LLM，并返回响应。工具调用扩展是按需启用的——当 enable_tool_calling=True 且提供了 ToolRegistry 时，它会进入一个受控循环，从 LLM 输出中解析 [TOOL_CALL:name:parameters] 标记，执行相应工具，并将结果反馈回去：

    工具调用解析使用正则表达式 r'\[TOOL_CALL:([^:]+):([^\]]+)\]' 从自由格式的 LLM 输出中提取结构化调用。这是一种刻意的权衡：虽然不如函数调用 API 健壮，但对于学习而言却透明得多。_parse_tool_parameters 方法提供了智能参数推断——如果原始参数包含 =，则解析键值对；否则，根据工具类型推断参数名（search → query，memory → action + query）。

    [TOOL_CALL:name:parameters] 格式是出于教学目的的选择。在生产环境中，你会切换到模型原生的函数调用 API（HelloAgents 通过带有 tools 参数的 llm.invoke 予以支持）。基于文本的格式使得解析-执行-反馈的循环完全可见且易于调试。

    来源: Chapter7-Building-Your-Agent-Framework.md, my_simple_agent.py

    提示词模板强制要求严格格式——每个 LLM 的回复都必须同时包含 Thought 和 Action——并明确指出“一次只能执行一步”，以防止模型将多个动作压缩到单次输出中。custom_prompt 参数允许你替换整个模板，这对于特定领域的 ReAct 变体非常有用：

    动作解析器从 tool_name[tool_input] 格式中提取工具名称和输入，将执行委托给 ToolRegistry.execute_tool，并将动作和观察结果一同追加到 current_history 中，作为下一次迭代的上下文。

## 工具系统层

### ToolRegistry — 统一的扩展点

`ToolRegistry` 是落实“一切皆为工具”理念的机制。它提供三个核心操作：`register_tool` / `register_function`、`execute_tool` 和 `get_tools_description`。最后一个操作至关重要——它生成的工具文档会被注入到 Agent 的提示词中，确保 LLM 始终掌握关于可用能力的准确信息。

工具既可以注册为类实例（需实现 `run` 方法），也可以注册为普通函数：

```python
# 基于类的注册
calculator = CalculatorTool()
registry.register_tool(calculator)

# 基于函数的注册
registry.register_function(
    name="my_calculator",
    description="Simple math calculator supporting +,-,*,/ and sqrt",
    func=my_calculate
)

    来源: my_calculator_tool.py, my_advanced_search.py

    高级搜索工具展示了多源集成模式。它会在初始化时检查可用的 API 密钥（Tavily、SerpAPI），注册已配置的来源，并在没有可用来源时优雅降级。搜索方法按优先级顺序遍历来源，返回首个成功的结果——这种模式使得工具能够从容应对个别提供商的宕机。

    后续展望

    HelloAgents 建立了架构骨架——统一的 LLM 接口、类型化消息、抽象 Agent 基类、工具注册表以及四种范式实现。该框架专为迭代式演进而设计。学习路径的下一阶段将为该结构增添深度：

    • 记忆系统与 RAG (Memory Systems and RAG ) —— 作为工具在注册表中实现，将 Agent 的上下文扩展至对话窗口之外
    • 上下文工程 (Context Engineering ) —— 使用结构化元数据和提示词组合策略扩展 Message 类
    • Agent 通信协议 (Agent Communication Protocols (MCP, A2A, ANP) ) —— 将 MCP 服务器作为工具暴露，使 Agent 间通信成为注册表操作

    上述每一项能力都通过相同的机制集成到 HelloAgents 中：registry.register_tool()。你在本章构建的架构并非原型——它是后续所有能力无需重构即可不断扩展的生产级骨架。
